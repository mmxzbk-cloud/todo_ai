## 1. 用户故事编写规范

### 1.1 三段式（强制）

每个 US 必须包含三块，顺序不可换：

```markdown
### US-0X：<动宾短语标题>

**用户故事**

作为 <角色>，我希望 <能力/目标>，以便 <业务价值>。

**故事详述**

- 关键流程/步骤一
- 边界条件 / 异常分支
- 与其他模块的依赖

**验收标准**

- AC X.1 `[前端]` <可测的具体行为>
- AC X.2 `[系统]` <可测的具体行为>
```

### 1.2 验收标准类别枚举（只能用这 7 个）

| 标注 | 适用范围 |
| --- | --- |
| `[前端]` | 页面、交互、跳转、按钮、表单校验 |
| `[系统]` | 后端逻辑、数据写入、状态机、API 行为 |
| `[性能]` | 响应时间、吞吐、并发、超时 |
| `[交互]` | 用户操作流（多步、二次确认、进度提示） |
| `[审计]` | 操作日志、变更留痕、可追溯 |
| `[文档]` | 交付文档、用户手册、差异说明 |
| `[交付]` | POC 报告、架构图、评估结论 |

### 1.3 拆分原则

- **一角色一动作 = 一个 US**；"批量导入"和"权限控制"不要塞进同一个 US
- 同一角色的多个动作可以并列在同一 US 的"故事详述"里，但验收标准必须能分别打勾
- 跨角色协作的场景，按主驱动角色归到一个 US，配角的动作放"故事详述"

## 2. 性能指标常用模板

```markdown
| 需求项 | 指标 |
| --- | --- |
| 单次接口响应 | P95 ≤ 3s |
| 批量任务 | 1000 条 ≤ 5min 完成（异步任务 + 进度查询） |
| 后台异步比对 | 单次 ≤ 5s，不阻塞主线程 |
| 列表分页加载 | ≤ 500ms（每页 20 条） |
```

写性能指标时遵循：

- 一定要写"百分位"（P95/P99），不要只写"平均值"
- 异步任务要说清"完成判定方式"（轮询/回调/进度查询）
- 列表类指标要带分页大小

## 3. 逻辑断言矩阵（第四章）

用 Given/When/Then 表格列出所有核心分支。覆盖原则：

- 每个 US 的"成功路径"至少 1 行
- 每个 US 的"失败/边界"路径至少 1 行
- 每个 P0 功能的开关 ON/OFF 至少各 1 行
- 跨环境/部署（SaaS / 私有化）的差异至少 1 行

样例：

```markdown
| Given | When | Then |
| --- | --- | --- |
| 启用考前人脸核验 | 考生无有效基准照 | 阻断开考，提示联系教师维护照片 |
| 启用考前人脸核验 | 比对通过 | 允许进入答题 |
| 比对失败达上限 | 无人工放行 | 不允许参加考试 |
| 比对失败 | 人工审核通过 | 允许继续考试流程 |
| 服务不可用 | 考生发起核验 | 按降级策略：阻断或仅人工（依配置） |
| SaaS 环境 | 配置身份验证 | 仅展示人脸核验 |
| 私有化环境 | 配置身份验证 | 与 SaaS 行为一致 |
```

## 4. 异常处理规范（第五章）

### 4.1 分场景子表（按需拆 5.1 / 5.2 / 5.3 ...）

```markdown
| 场景 | 用户提示 | 系统行为 |
| --- | --- | --- |
| 无摄像头权限 | 请允许使用摄像头后重试 | 阻断，可提供帮助链接 |
| 采集超时 | 未检测到人脸，请正对摄像头重试 | 计次失败 |
| 比对不通过 | 身份验证未通过，可重试或联系监考 | 计次；达上限进入人工队列 |
```

### 4.2 异常返回 JSON 示例（强制）

第五章末尾必须给一个标准异常返回 JSON，结构上至少包含：

- 业务主键（examId / orderId / userId 等）
- 当前阶段/状态
- 重试计数（如有）
- 人工审核状态（如有）
- `errors[]`：每条含 `code` / `message` / `suggestAction`

```json
{
  "summary": {
    "examId": "EXAM_20260427001",
    "studentId": "20260001",
    "phase": "PRE_EXAM",
    "autoVerifyStatus": "FAILED",
    "retryCount": 3,
    "manualReviewStatus": "PENDING",
    "errors": [
      {
        "code": "FACE_MISMATCH",
        "message": "人脸比对未通过",
        "suggestAction": "RETRY_OR_MANUAL"
      }
    ]
  }
}
```

## 5. 附录章节细则

### 5.1 流程图（ASCII）

用代码块 + ASCII 字符画即可，不引图床、不上传图片。样例：

```
┌─────────────────────────────────────┐
│ 教师端：基准照维护                   │
│  单条上传 / 批量 ZIP / 查询 / 删除   │
└──────────────┬──────────────────────┘
               │ 写入
               ▼
┌─────────────────────────────────────┐
│ 学生信息管理：基准人脸照片            │
└──────────────┬──────────────────────┘
               │
       ┌───────┴───────┐
       ▼               ▼
┌─────────────┐  ┌─────────────┐
│ 考前核验 P0 │  │ 考中抽检 P1 │
└──────┬──────┘  └──────┬──────┘
       │                │
       ▼                ▼
   通过/失败 ─► 人工介入 ─► 放行/拒绝
       │
       ▼
   进入答题
```

### 5.2 角色与权限矩阵

- 用 ✅ / ❌ / —（不涉及）/ 文字限定（如"本机构"、"依权限"）四种符号
- 每行一个功能，每列一个角色

### 5.3 待确认项（A.4）

把评审里没拍板的开放问题列在这里，编号即可：

```markdown
1. <开放问题一>：<两种以上选项，及各自风险/收益>
2. <开放问题二>
```

**规则**：

- 凡是正文里写不下决断的（阈值、技术选型、隔离方式…），都要在 A.4 留痕
- A.4 一旦在评审中拍板，把结论合并回正文，并在版本记录里写"v1.1 关闭 A.4 第 N 条"

## 6. 版本记录约定

```markdown
| 版本 | 日期 | 说明 |
| --- | --- | --- |
| v1.0 | 2026-04-27 | 初稿：环境统一、考前核验、教师端照片、人工介入、考中方案待选、技术评估 |
| v1.1 | 2026-05-10 | 关闭 A.4 第 1/3 条；考中方案锁定为"监考频度截帧"；新增 US-07（监考端告警） |
```

规则：

- 主版本号（v1.x → v2.0）：架构级变更、范围大改、不向下兼容
- 次版本号（v1.0 → v1.1）：新增章节、关闭待确认项、新增 US
- **不删行**：旧版本说明永远保留
- 日期格式：`YYYY-MM-DD`

## 7. PRD Self-Check Checklist

写完一版 PRD，提交前逐项打勾：

### 结构完整性

- [ ] 七章节都在（哪怕某章只写"本期不涉及"）
- [ ] 文件名符合 `prd/<主题>-PRD-<副标题>.md` 规范
- [ ] 顶部一级标题与文件名主题一致

### 用户故事

- [ ] 每个 US 都是"用户故事 + 故事详述 + 验收标准"三段式
- [ ] 每条 AC 都有类别标注（`[前端]` `[系统]` `[性能]` `[交互]` `[审计]` `[文档]` `[交付]`）
- [ ] 每条 AC 都是可测的（不写"用户体验良好"这类不可测描述）
- [ ] 没有把多个角色 + 多个动作塞进同一个 US

### 非功能 & 矩阵

- [ ] 性能指标带百分位（P95/P99），不只是平均值
- [ ] 第四章断言矩阵覆盖了每个 US 的成功路径 + 失败路径
- [ ] 第四章覆盖了部署环境/开关 ON-OFF 差异（如有）

### 异常处理

- [ ] 第五章给了至少一组分场景异常表
- [ ] 第五章末尾有 JSON 异常返回示例
- [ ] 重试次数、人工介入门槛在异常表里能看到

### 附录

- [ ] A.1 流程图用 ASCII 代码块
- [ ] A.2 角色权限矩阵符号统一
- [ ] A.4 列出了所有评审待拍板项

### 版本记录

- [ ] 当前版本在版本表里
- [ ] 升版本时没有删旧行

### 不该出现的内容

- [ ] 没有"我"、"我们"、"小弟"这类口语
- [ ] 没有具体的实现代码（PRD 只写行为契约，不写实现）
- [ ] 没有"约/大概/差不多"等模糊措辞（要么给数，要么进 A.4）
- [ ] 没有 P2 及以下的能力堆砌

## 8. 典型反例（避免）

### 反例 1：验收标准不可测

```markdown
- AC 2.1 用户体验流畅，加载速度快   ❌
- AC 2.1 `[性能]` 答题主接口 P95 ≤ 1.5s  ✅
```

### 反例 2：用户故事塞了一堆角色

```markdown
US-03：教师上传 + 学生查看 + 管理员审核   ❌

拆成三个：
US-03：教师维护基准照
US-04：学生查看自己的核验记录
US-05：管理员审核基准照
```

### 反例 3：阈值随手写死

```markdown
- AC 2.4 比对阈值默认 0.85   ❌（PRD 不该锁死阈值）
- AC 2.4 `[系统]` 比对阈值可配置（档位：高/中/低），默认值由 US-06 评估报告给出  ✅
```

### 反例 4：升版本时改了旧版本说明

```markdown
| v1.0 | 2026-04-27 | 增加了考中抽检和监考告警   ❌（v1.0 当时没这内容）

应该：
| v1.0 | 2026-04-27 | 初稿：考前核验、教师端照片
| v1.1 | 2026-05-10 | 新增考中抽检、监考告警       ✅
```

## 9. 修订模式（已有 PRD 升版本）

收到"改 PRD"类需求时：

1. 先读 `prd/<现有文件>.md` 全文，确认当前版本号
2. 列出"准备改的章节清单"给用户确认（哪些 US 新增/修改、哪些 AC 调整、哪些 A.4 关闭）
3. 用 StrReplace 精确改动受影响段落，**不要重写整篇**
4. 在第七章追加一行新版本记录，写明本次变更
5. 把改后文件路径告诉用户

修订时严禁：

- 改旧版本号对应的说明
- 直接整篇 rewrite 导致 diff 看不清
- 自己临时新增类别标注（只能用 7 个枚举之一）
